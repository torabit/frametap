# frametap 設計

## 目的

Dark Souls Remastered (60fps) の wrong warp を練習するために、プレイ中の DualSense の入力をフレーム単位で確認する。`L1 + ↑` と `R1` を 1F ずらしで押せているかを、試行ごとに目で読み取れる状態にする。

コマンドの成否は判定しない。入力を正確に並べるところまでが責務である。

## 確定した前提

| 項目 | 値 |
| --- | --- |
| 対象ゲーム | Dark Souls Remastered、60fps |
| 1F | 16666.7µs |
| デバイス | DualSense または DualShock 4 |
| 接続 | USB 有線 |
| ゲームとの関係 | Steam Input 経由でプレイ中に並走する |
| 表示先 | サブモニタの always-on-top ウィンドウ |
| 実行環境 | Windows ネイティブ |
| 言語 | Rust |

## スコープ

やること。

- 物理 HID レポートの記録と、ボタン押下と離しのイベント化
- イベント間の相対時間差の F 換算と表示
- 十字キーと左スティックを 8 方向に量子化して方向入力として扱う
- 直近 5 試行の比較表示

やらないこと。

- コマンドパターンの定義と成否判定
- ゲーム内フレーム境界との同期
- Bluetooth 接続への対応
- ブラウザ版
- デバイスへの書き込み (LED、rumble、センサ有効化)

## 入力経路

**hidapi で物理 HID デバイスを読み取り専用で開く。** 専用スレッドで `read_timeout(-1)` をブロッキングし、レポート 1 件ごとに起床する。

この経路を選ぶ根拠。

- ゲームコントローラの top-level collection は Windows の定義で Shared access であり、入力レポートは全ハンドルに複製配信される。Steam がハンドルを持っていても開ける
- hidapi の Windows backend は `FILE_SHARE_READ | FILE_SHARE_WRITE` 固定で、排他オープンを指定する API が存在しない
- ブロッキング read はレポート到着で起床するので、タイマー分解能とポーリングのジッタが関与しない

却下した経路と理由。

- XInput: Windows の Steam Input は仮想ゲームパッドのドライバを使わず、overlay が注入先プロセス内で API を hook する方式である。hook されていない第三者プロセスからは仮想パッドが存在しない。DualSense は素の XInput にも現れない
- Windows.Gaming.Input: ポーリング API であり、フォーカスのあるウィンドウを要求する
- Raw Input: `WM_INPUT` は `RAWHID.dwCount` で複数レポートをバッチ化するため、受信時刻がバッチ単位になる。デバイス時刻を使えばこの欠点は消えるが、raw input device class ごとにプロセス内 1 window という制約があり、Microsoft のドキュメント自身がライブラリから使うべきでないと書いている
- SDL3: レポートのパースを省ける利点はあるが、依存が重く、時刻の粒度が SDL の内部処理に依存する。デバイスが DualSense と DS4 に確定しているため利点が効かない
- GameInput: µs 単位のタイムスタンプを OS が付ける唯一の経路だが、背景入力のコールバックが発火しない未解決の GDK issue がある。Rust バインディングも存在しない

書き込みは一切しない。output report と feature report を送ると Steam と取り合いになる。Linux の `hid-playstation` に該当するコメントがある。「Steam のような hidraw アプリも feature report を出すので別のレポートのデータが返ってくることが多い」。

## 時刻モデル

### 一次時刻源はレポート内のデバイス時刻

ホストの受信時刻 (QueryPerformanceCounter) を一次に使うと、スケジューリングジッタが 4ms の量子化に上乗せされて 1F 判定が壊れる。デバイスが自分で打った時刻を使えば量子化誤差がレポート間隔に収まる。

| デバイス | フィールド | 幅 | 公称単位 | wrap 周期 |
| --- | --- | --- | --- | --- |
| DualSense | `sensor_timestamp` | 32bit | 0.33µs | 約 23.6 分 |
| DualShock 4 | `sensor_timestamp` | 16bit | 5.33µs | 349ms |

USB 接続のレポート間隔は 4ms (250Hz) である。1F に対する量子化誤差は 4ms、つまり ±0.24F。0F は 0 から 4ms、1F は 12.7 から 20.7ms、2F は 29 から 37ms の範囲に観測されるため、識別に足りる。

### 単位は決め打ちせず校正する

DualSense の公称単位は 0.33µs だが、機種と FW によって 1µs 単位の分岐が SDL に存在する。決め打ちすると特定の個体で F 数が定数倍ずれる。

起動後 2 秒のレポートを使い、QPC の経過とデバイス時刻の経過の比からスケールを推定する。以降その値を使う。推定値は画面に常時表示する。想定単位から 20% 以上外れた場合は警告を出す。

### wrap の曖昧さは QPC で解消する

DS4 は 349ms で回る。無入力が 349ms を超えると、前回値との比較だけでは wrap 回数が決まらない。QPC の経過時間から wrap 回数を推定する。349ms 単位の判別に必要な精度は ±数 ms なので、ジッタのある QPC でも足りる。

デバイス時刻を精度に、QPC を wrap の曖昧さ解消に使う。この役割分担を崩さない。

### 絶対フレームグリッドを持たない

ゲーム内のフレーム境界は外部プロセスから観測できない。測るのはイベント間の相対時間差だけである。

F 数は経過µs を 16666.7 で割り、小数第 1 位まで表示する。整数に丸めると 12.7ms と 20.7ms がどちらも `1F` になり、境界付近で判断を誤る。

fps は設定で 30 に切り替えられるようにする。

## モジュール構成

データが一方向に流れる 5 段に切り、スレッドの配線を `app` に置く。各段は上流を知らない。

| モジュール | 責務 | 依存 |
| --- | --- | --- |
| `hid_source` | hidapi でデバイスを開き、ブロッキング read で生レポートを 1 件ずつ返す。受信直後に QPC を打つ | hidapi、windows |
| `report_decode` | 生バイトを `PadState` (ボタン bitflags、スティック、`device_ts`、`seq_number`) へ変換する純関数 | bitflags |
| `timeline` | `PadState` 列の差分から `InputEvent { kind, button, at_us }` を生成する。デバイス時刻の校正と wrap 処理もここ | `report_decode` の型 |
| `history` | 直近 30 秒のイベントを ring buffer で保持する。書き込みと読み出しの API だけを公開 | `timeline` の型 |
| `ui` | egui で `history` を読んで描く | `history` の読み出し API |
| `app` | スレッドの起動と配線 | 全モジュール |

`report_decode` と `timeline` が純粋なので、実機なしでテストできる。ここが品質の要である。

スレッドは 2 本。

- 入力スレッド: `hid_source` から `history` まで回す
- UI スレッド: eframe のループで `history` を読む

250Hz 書き込みと 60Hz 読み出しなので `Mutex<RingBuffer>` で足りる。lock-free は要らない。ロック保持は push と snapshot のコピーの間だけに絞る。

クレートは hidapi、eframe、egui、bitflags、windows。windows crate は QPC のためだけに使う。

## 設定

実行ファイルと同じディレクトリの `frametap.toml` 1 枚に置く。項目は以下だけにする。

| キー | 既定値 | 意味 |
| --- | --- | --- |
| `fps` | 60 | F 換算の基準 |
| `trial_gap_ms` | 300 | 試行を区切る無入力時間 |
| `stick_deadzone` | 0.5 | 左スティックを方向入力と見なす閾値 |
| `trials_shown` | 5 | 数値リストに積む試行数 |

ファイルが無ければ既定値で動く。

## 表示

ピアノロールと数値リストを縦に並べる。

### ピアノロール

- 縦軸はボタン。その試行で押されたボタンだけ行を作る
- 横軸は時間。1F ごとに薄い縦線、5F ごとに濃い線を引く
- 試行の最初の押下を 0F とする
- 押している区間をバーで描く
- 十字キーの `↑` と左スティックの `↑` は別の行にする。どちらで入力しているかが見えないと原因を切り分けられない

### 数値リスト

各試行 1 行。押されたボタン名とその押下 F だけを並べる。持続 F はバーの長さで読めるので数値には出さない。

直近 5 試行を縦に積む。うまくいった試行と外した試行を見比べられる。

### 試行の区切り

入力が 300ms 途切れたらそこで区切り、直前のまとまりを固定表示する。常時スクロールする帯ではプレイ中に横目で 1F ずれを読めない。手を止めた瞬間に結果が読める形にする。

区切り時間は設定可能にする。これは成否の判定ではなく描画の区切りである。

### ウィンドウ

`ViewportBuilder::with_always_on_top()` を使う。サブモニタに置く。

### 方向入力の量子化

左スティックは 8 方向に量子化する。デッドゾーン閾値は設定可能にする。アナログの生値はこの用途に不要である。

## エラー処理

**取りこぼしを黙って繋げない。** `seq_number` が飛んだら、その区間を履歴上でグレーの帯として明示する。欠落を補間すると存在しない F 数が出る。

**スケール校正の逸脱を警告する。** 想定単位から 20% 以上外れたら画面に警告を出す。黙って定数倍ずれた F 数を出すのが最悪である。

**デバイスの抜き差しに耐える。** 見つからない場合と途中で抜かれた場合は UI に明示し、1 秒ごとに再接続を試みる。履歴は消さない。

## テスト

- `report_decode`: DualSense と DS4 の実レポートのバイト列を固定データで持ち、期待する `PadState` に変換されることを検証する
- `timeline`: 合成した `PadState` 列を入れて期待する `InputEvent` 列と F 数が出ることを検証する。wrap、取りこぼし、スケール校正をそれぞれ独立にテストする
- `history`: ring buffer の満杯時の上書きと試行の区切り
- `ui`: 自動テストしない

実機検証は 2 項目。

- ウィンドウを別ウィンドウで覆った状態で記録が壊れないか
- Steam 起動中に物理 DualSense の HID を開けるか

1F ずれそのものは人間の手で再現できない。代わりに下限と上限を押さえる。下限は同時押しが 0F 付近に出るか。上限は意図的に間を空けた入力が期待する F 数になるか。

## 品質ゲート

`.coupling.toml` を置き、`hid_source` を高 volatility、`report_decode` と `timeline` を core subdomain として分類する。

```
cargo coupling --check --min-grade=B --max-circular=0 ./src
```

実装計画の各ステップの完了条件に入れる。

## 未検証の前提

実装時に確かめる。外れた場合は経路の選定に戻る。

- Steam 起動中に物理 DualSense の HID を開けること。ドキュメント上は Shared access だが、直接の実測報告は見つかっていない。DS4Windows の double input が起きる事実からの推論である
- ブロッキング read で起床する設計ならタイマー分解能が関与しないこと。ウィンドウが隠れても記録が壊れない見込みだが未検証
- `dualsense-rs` 系のクレートが `sensor_timestamp` と `seq_number` を API に出しているか。確認できなかったため生バイトを自前でパースする方針にしている
